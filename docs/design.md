# Snipher 設計書

## 1. 概要

Snipher は「**日本語のみ**」に対応した、if 構文ベースのルール解析と確率的テーブル生成を組み合わせた
極小パラメータのAIモデルである。

大きな設計思想はひとつ:

> **動詞・助動詞・名詞・助詞・文構造を「あらかじめ決めておく」ことによって、
> 量子化された大規模言語モデル(例: 1.2B パラメータ)よりも圧倒的に少ない
> パラメータで、日本語の構文解析と高速な文章生成を実現する。**

Snipher の全パラメータは:

| 要素 | 数 | 内容 |
|------|-----|------|
| 単語テーブル | 470 エントリ | 動詞90 / 形容詞94 / 名詞148 / 助詞39 / 助動詞24 / 副詞26 / 接続詞14 / 文型12 / コーパス25文 |
| 確率式の重み | 6 個 | `alpha, beta, gamma, delta, epsilon, zeta` |

**合計 476 個** のパラメータしか持たない。これは 1.2B(12億) と比べて約 **252万倍** 小さい。

## 2. なぜ「パラメータが少ないと速い」のか

量子化(int8/int4)は「重みの精度を落とす」だけで、重みの**数**は減らない。
1.2B モデルは量子化しても 12億個の演算が必要になる。

Snipher は「次に来る単語」を、辞書引き(if 構文のルール)と
ごく少数の候補に対するスコア計算だけで決めるため、1文の生成は
テーブル走査 + 6項の加算のみで完結する。つまり:

- モデルロード: JSON 数十 KB(メモリ常駐不要)
- 1トークン生成: 数百回の浮動小数演算
- GPU 不要。CPU の1コアで数千〜数万文/秒が可能(理論上)

これが「量子化よりも圧倒的に少ないパラメータで、圧倒的なトークン出力速度を実現する」の
根拠である。

## 3. LFM2.5 1.2B JP の解析から導いた知見

1.2B 級の日本語 LLM(LFM2.5 1.2B JP を含む)の出力の統計的振る舞いを観察すると、
日本語文の生成は次の低次元の要因に強く支配されていることが分かる:

1. **文型(構文パターン)の選択** — 「〜は〜を〜ます」「〜は〜です」等の
   高頻度パターンが出力の骨格を決める。エントロピーは低く、少数の文型で
   大部分の文をカバーできる。
2. **述語(動詞・形容詞)の選択** — 述語が文の意味的骨格を決め、
   述語が要求する格(を/が/に/へ)が後続要素を支配する。
3. **助詞・助動詞・活用語尾の鋭い分布** — 「ます/です/た/ない」等は
   文脈が決まればほぼ一意に決まる(低エントロピー)。小さいテーブルで高精度に再現できる。
4. **話題(トピック)の意味クラスの連続性** — 同じ話題の名詞・動詞は
   意味クラス(食事/移動/感情…)が一致しやすい。
5. **文体(です・ます体 / だ・た体)の一貫性** — 文内で文体マーカーが混ざらない。

この知見を6つの特徴量に圧縮し、独自の確率式として定式化した。

## 4. 独自確率式

候補トークン `w` のスコア `S(w)` を次の重み付き和で定義する:

```
S(w) = alpha * log P_freq(w | 直前)      … 頻度事前分布(コーパス統計)
     + beta  * log P_trans(pos_w | pos_prev) … 品詞遷移(マルコフ)
     + gamma * Q_role(w, 述語)           … 格・役割適合(動詞の要求する助詞)
     + delta * Q_inflect(w, 前後)        … 活用整合(活用形と助動詞の一致)
     + epsilon * Q_register(w, 文体)     … 文体整合(です/ます体の一貫性)
     + zeta   * Q_topic(w, 話題)         … トピック一貫性(意味クラスの一致)
```

確率分布はソフトマックス:

```
P(w) = softmax( S(w) / T )    (T = temperature, 既定 0.8)
```

### 各項の意味と実装

| 記号 | 重み | 意味 | 実装 |
|------|------|------|------|
| `alpha` | 1.2 | コーパス由来の bigram/unigram 頻度の対数尤度 | `corpus.json` 25文からスムージング付きで推定 |
| `beta` | 1.0 | 品詞遷移行列(名詞→助詞→動詞→助動詞→句点 等) | `probability.py` の `_TRANSITIONS` |
| `gamma` | 1.0 | 動詞の自他と助詞の整合(他動詞なら「を」等) | `_ROLE_BONUS` テーブル |
| `delta` | 0.8 | 活用形と後続助動詞の整合(連用形+ます 等) | `inflection_score` |
| `epsilon` | 0.6 | 文体マーカーの一貫性(です/ます vs だ/た) | `register_score` |
| `zeta` | 1.5 | 話題と述語の意味クラスの一致 | 名詞/動詞の `t`(タグ)の共通集合 |

生成は「**述語を先に決め、その要求に合わせて名詞と助詞を選ぶ**」述語中心の手順で行い、
文型ごとに動詞の自他を if 構文で制約する(例: 目的語「を」を要求する文型では他動詞のみを候補とする)。

## 5. アーキテクチャ

```
snipher/
  data/            # モデルの全知識 = JSON テーブル(これがパラメータ)
    verbs.json       動詞(表記・読み・活用型・自他・要求助詞・意味タグ)
    adjectives.json  形容詞(い/な)
    nouns.json       名詞(意味クラス・タグ)
    particles.json   助詞(機能・役割)
    auxiliaries.json 助動詞(意味カテゴリ)
    other.json       副詞・接続詞・感動詞
    patterns.json    文型(文構造をあらかじめ決める)
    corpus.json      解析・頻度推定用の教師コーパス
    config.json      確率式の重み6個 + 温度 + トピック親和性
  lexicon.py       テーブルのロード・検索
  morphology.py    活用処理(五段/一段/サ変/カ変・音便・形容詞)
  parser.py        トークン化・品詞推定・文構造/助動詞/要点の抽出
  probability.py   独自確率式 + softmax サンプリング
  generator.py     文型スロットの確率的な埋め込み
  engine.py        統括ファサード
  api.py           FastAPI(UI + REST API)
```

### 解析器(parser)が出力するもの

- **トークン列と品詞**(辞書最長一致 + 活用形の逆引き)
- **文構造**: 文型(平叙文/状態文/名詞述語文/疑問文/理由文/逆接文/推量文 等)・時制・
  主題/主語/目的語の有無
- **助動詞**: です/ます/た/ない/たい 等とその意味カテゴリ(断定・過去・否定・希望…)
- **要点(キーポイント)**: 述語(動詞/形容詞)、役割(主題/主語/対象/場所…)、助動詞
- **話題(トピック)**: 「は」が受ける名詞

## 6. デプロイ

- **Vercel**: `pyproject.toml` の `tool.vercel.entrypoint = "snipher.api:app"` により
  `snipher/api.py` を ASGI アプリとしてデプロイする
  (ルートは Serverless Functions の Python ランタイムで動作)。
  依存は `requirements.txt` だけでなく `[project.dependencies]` にも定義し、
  Python ランタイムで確実に解決できるようにする。
- **Render**: `render.yaml` により Web サービスとして
  `uvicorn snipher.api:app --host 0.0.0.0 --port $PORT` で起動。

どちらも依存は `fastapi` / `uvicorn` / `pydantic` のみ。外部サービス・GPU・
大容量モデルファイルは一切不要。

## 7. 限界と今後の拡張

- 語彙はテーブル内の約500語に限られる(未知語は1文字ずつ扱う)。
- 意味的な自然さは統計サンプリングのため確率的に揺らぐ。
- 拡張方向: テーブルの拡充(語彙増)、コーパス増による頻度推定の精緻化、
  係り受け木の導入、複数文の談話一貫性、および重みの自動チューニング。

この弱点を補うのが **LFM2.5-1.2B-JP とのハイブリッド補正**(docs/lfm.md 参照)である:
各スロット決定の softmax 確率の重み平均 = confidence を計算し、
不確実な下書きだけをニューラル補正に渡すことで、
「速さ(全件ルール)」と「賢さ(不確実な件のみ LFM)」を両立する。
助動詞・文体の欠落は polisher がルールで補完するため、
ニューラルモデルが無い環境でも日本語としての下限は保たれる。

> 本設計は「量子化よりパラメータを減らす」というコンセプトの実証(試み)であり、
> 汎用 LLM の性能を置き換えるものではない。ただし、日本語の構文解析と
> 高頻度文型の生成という限定タスクでは、極小リソースで実用的な速度を達成できる。
